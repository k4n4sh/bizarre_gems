# Visual work

## How to approach a design change
1. Agree on the target picture first: a static mockup of one screen, a human designer's
   frame or an asset-pack reference the user approves. No Godot code before that.
2. One main reference and one sentence of style. Extra references are hints only.
3. One screen or one element per stage, on a branch, committed; revert with git, not
   with flags inside the code.
4. Use real assets (artist, purchased or free packs such as Kenney). Never ship art that a
   script generated procedurally.
5. Show before/after screenshots without judging them; ask what the user sees.
6. Do not mix old and new looks on one screen.

## What went wrong on 2026-10-26 (rolled back, tag `before-redesign`)
- A machine-written Art Bible (pixel gems 16×16, pixel fonts, gold bevel frame, popup
  plates) was implemented literally without an approved picture.
- Gems, frame, buttons and icons were generated by a Python script: it read as
  "made by a neural network".
- New styling was hooked into the existing HUD, whose slots auto-scale their content and
  which has four layouts; fixes piled on fixes. Redesign the layout instead of patching it.
- The first stage changed too little, the next one too much at once.

## The user's fixed decisions
- Keep the current gems (no pixel art).
- Classic: landscape only on Android; Bright Run: portrait with the top HUD.
- Desktop/landscape keeps equal space on both sides of the field (no side panel: it would
  push the field away from the left thumb on Android).
- Nothing covers the field: no plates. Praise and hit texts float up and fade.
- One knock-out animation: gems fly to the score; no gems falling off the board.
- Liked: recessed sockets without rings, the field itself as a recess in the felt.
- Font: Handjet was the only candidate liked (variable axes ELSH 2, ELGR 1; bold for
  numbers). Use few sizes, the same everywhere.
- Undecided: the field frame.
